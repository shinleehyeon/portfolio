## 1. 지원동기

콘텐츠가 같아도 시청이 시작되는 순간이 다르다는 점이 티빙을 고른 이유입니다. 2026년 10월 메트로신문에서 본 퀵 VOD가 그 계기였습니다. 같은 작품을 넷플릭스와 동시에 틀어도, 티빙은 방송 시작 5~10분 뒤부터 첫 장면을 볼 수 있고 넷플릭스는 방송 종료 후 1~2시간을 기다립니다. 수급이 아니라 시청이 열리는 속도를 설계하는 회사로 읽혔습니다. 작품별 24시간 팬톡도 같은 선입니다. SNS로 빠져나가던 대화를 플랫폼 안으로 가져와, 보는 경험과 말하는 경험을 한 화면에 붙입니다. KBO를 2031년까지, UFC를 2029년까지 가져가는 결정은 생중계라는 끊기면 끝나는 트래픽을 웹·앱·TV에서 동시에 받아야 한다는 뜻입니다. 채용공고의 Web Core가 홈부터 계정·구독·결제 여정을, Player가 초기 재생·버퍼링·화질 지표를 본다는 문장은 이 전략의 실행 단위로 보였습니다. 나정민 님이 프론트엔드를 티빙의 앵커라고 한 이유와도 맞습니다. 기능이 아니라 고객이 실제로 만나는 마지막 화면을 책임지는 자리입니다.

직무를 프론트엔드로 고른 이유는, 화면을 만들기 전에 사용자가 어디서 멈추는지를 먼저 보고 싶어서입니다. 데이터를 읽지 못하면 화면을 고치지 않는 것이 제 기준입니다. 당근 알바에서는 신고 직전 내림·재등록 패턴을 보고 FDS를 넣었고, EffectGen에서는 이탈 지점이 안 보이면 개선이 감이 되어 Mixpanel 이벤트를 먼저 깔았습니다. 서유림 님이 말한 클릭과 스크롤이 닿는 순간의 몰입이, 제가 일을 고르는 기준과 같습니다.

## 2. 직무 관련 전문성을 쌓기 위해 한 일

폭을 먼저 넓힌 뒤, 같은 문제를 다른 레이어에서 반복해서 풀었습니다. 웹은 Next.js 15와 React 19로 EffectGen을 출시했고, 구독 결제와 비동기 생성 상태를 서버 액션과 React Query로 나눴습니다. 앱은 React Native와 Expo로 음성(STT), BLE·WiFi Dual 연결, QR 결제, 지도 탐색을 구현했습니다. 웹뷰는 당근 알바에서 네이티브 브릿지·로딩·스크롤이 어색한 지점을 지표로 찾아 고쳤습니다. 실시간은 WebSocket 채팅과 SSE 스트리밍, Optimistic UI로 대기 시간을 감췄습니다. 결제와 인증은 Toss Billing Key 자동결제, 프로레이션, 결제일 기준 사용량 리셋, 인증 8종 상태 분기를 설계했습니다. 생성은 Replicate webhook과 Sora Text/Image-to-Video로 받고, 결과는 Supabase Storage로 백업했습니다. 행동 데이터는 Mixpanel·GA4·Meta Pixel을 한 `track()`으로 묶고 템플릿별 조회·선택·다운로드를 집계했습니다. AWS 3tier는 Terraform과 GitHub Actions로 재현 가능하게 만든 수준입니다. Micro Frontend, DRM, Smart TV 플레이어 코어는 아직 없습니다. 입사 후 웹뷰와 공통 모듈부터 익히고, Player 지표는 현업 코드와 재생 로그를 보며 붙이겠습니다.

## 3. 앞에서 말하지 못한 문제 해결

당근 알바에서 불법 공고는 신고 횟수만으로 줄지 않았습니다. BigQuery로 보니 악성 사용자가 신고 임계치 직전에 공고를 내렸다가 다시 올리는 회피 패턴이 있었습니다. 횟수 제재는 표면만 막는 구조였습니다. 작성 화면에 "이 공고가 이해하기 어렵지 않나요?" 넛징을 넣고, 수정·재등록 주기까지 추적해 신고 3회 이상 공고는 AI가 탐색·제재하도록 바꿨습니다. 이후 해당 유형 불법 공고가 줄어든 것을 데이터로 확인했습니다.

같은 기간 인증 8종(사업자·재직증명·본인·신분증·얼굴·금융인증서·계좌·지역) 조합이 화면과 기능을 갈랐습니다. 조건문을 나열하면 인증이 늘 때마다 분기가 깨집니다. 인증 상태를 한 구조로 모아, 조건이 추가돼도 분기 전체를 건드리지 않게 만들었습니다. 알파에서만 되던 채팅 기능은 프론트를 검증한 뒤 백엔드 처리 누락을 찾았고, "버그가 있다"가 아니라 원인 가설과 함께 백엔드 리드에게 전달해 닫았습니다.

EffectGen에서는 생성이 끝나도 이미지가 사라지는 문제가 있었습니다. Replicate 임시 URL이 만료되기 전에 Supabase Storage로 옮기지 못하면 결제한 결과가 비었습니다. webhook으로 완료를 받고, 백업 실패 시 5회 재시도·30초 타임아웃 후 task를 FAILED로 내려 유실을 막았습니다. 티빙의 결제 이탈·재생 대기·팬톡 끊김도 같은 순서로 보겠습니다. 화면이 아니라 데이터가 가리키는 회피 구조를 먼저 고칩니다.

## 4. 입사 후 포부

입사 직후 Web Core에서 웹뷰와 구독·결제 여정을 안정적으로 맡겠습니다.

단기에는 티빙 앱 웹뷰 화면의 로딩·스크롤·브릿지 이질감을 줄이고, 계정·구독·결제 흐름의 이탈 구간을 지표로 확인해 고치겠습니다. 당근 알바에서 마케팅 웹뷰를 붙이고, EffectGen에서 Toss 빌링·프로레이션·기간말 해지를 운영한 경험이 이 업무와 가장 가깝습니다. 김형래 님이 하이브리드 웹과 Yarn workspace로 DX를 올린 것처럼, 반복 UI는 공통 모듈로 빼 배포와 수정 비용을 줄이겠습니다. 나정민 님이 말한 대로 기능이 되기만 하면 되던 단계는 지났고, 코드 품질과 성능이 같이 가야 하는 자리입니다.

중기에는 서유림 님이 맡은 팬톡처럼 실시간 채팅의 연결·재연결·메시지 순서를 웹 성능 예산 안에서 유지하는 일을 하겠습니다. 정래한 님이 말한 대로, 직접 쓰는 서비스의 끊김을 알고 있어야 화면에서 놓치는 지점이 줄어듭니다. 퀵 VOD와 팬톡이 같은 작품 화면에 붙어 있으므로, 재생 대기와 채팅 상태를 따로 보지 않겠습니다.

장기적으로는 Player 도메인의 초기 재생·버퍼링·화질 지표를 웹 화면과 같이 보겠습니다. SLOP에서 생성 지연 중에도 폴링을 포기하지 않게 한 이유와, 퀵 VOD가 방송 중에도 첫 장면을 여는 이유는 같습니다. 재생 버튼을 누른 뒤 영상이 나오기까지를 하나의 경험으로 설계하는 일이 제가 남기고 싶은 자리입니다. Smart TV와 DRM은 입사 후 플레이어 코어와 로그를 보며 붙이겠습니다.
